========================= LINKS =========================
SUMMARY: The site's navigation chrome and shipped CTAs contain numerous dead controls. The most severe is the Footer: its three link columns render bare <a> tags with NO href attribute (so 9 links per locale are completely unclickable), and the "legal" array renders as <span> (not even an anchor) pointing at a TERMS/privacy page that does not exist as a route. All email/contact forms post to action="#" with no backend wired (no page passes an `action`), so every form submit reloads the page and loses input. The locale switcher and main nav links are correctly implemented (live-locale gating works). The design-system page's # placeholders are acceptable since it is an internal noindex reference page. Concrete destinations for each footer/CTA item are given below.

========================= HOVER =========================
SUMMARY: The codebase has a systemic hover/transition gap rooted in two patterns. (1) The confirmed Button.astro bug: primary/ghost variants gate every hover/active effect behind Tailwind's `enabled:` variant, which compiles to the CSS `:enabled` pseudo-class. `:enabled` matches ONLY form controls (button/input/select/textarea), never `<a>`. Since Button renders `<a>` whenever `href` is set, EVERY primary/ghost link-button on the site has ZERO hover and active feedback — this includes the two main hero CTAs, the books-promo CTA, the contact CTA, the 404 recovery buttons, and the book-detail "get book" button. The same `enabled:` classes in EmailCapture.astro and ContactForm.astro are on real `<button>` elements, so those DO work (correct distinction confirmed). (2) A large class of hover effects animates color/transform on non-anchor/non-button elements (h2/h3/div), which the global `a,button { transition }` rule in global.css does NOT cover, so those state changes snap instantly instead of easing — this is the "not smooth" sensation. The Svelte quiz's primary/ghost/cta/nav buttons have no `:hover` rule at all. Breadcrumbs on the two book pages are plain spans with no hover. And there is no `:focus-visible` treatment anywhere on the site — keyboard users get only the inconsistent UA default outline (often suppressed by `outline-none` on form inps). Recommended baseline everywhere: accent #3F6B5E hover, ~0.18s ease transitions, and an explicit focus-visible ring (e.g. box-shadow 0 0 0 3px rgba(63,107,94,0.35)).

[CRIT] Button primary/ghost link-buttons have ZERO hover/active (enabled: never matches <a>)
  @ src/components/common/Button.astro:46-53
  WHAT: variantClasses.primary and .ghost gate all hover/active styling behind Tailwind `enabled:hover:*` / `enabled:active:*` variants (lines 48-49 primary, 52-53 ghost). Tailwind compiles `enabled:` to the `&:enabled` selector, i.e. the CSS `:enabled` pseudo-class. Per the CSS spec, `:enabled` matches ONLY form-associated elements (button, input, select, textarea, optgroup, option, fieldset) and NEVER an `<a>`. The render block (lines 84-89) emits `<a href=...>` whenever `href` is set. Therefore every primary/ghost Button that has an href produces an anchor on which none of the bg-accent-deep, -translate-y-px, shadow, or active rules ever apply — the buttons are visually dead on hover/press. Confirmed against tailwindcss 4.3.0 in package.json. The `text` variant (lines 54-57) correctly uses plain `hover:` and works on <a>.
  FIX:  Drop the `enabled:` prefix and instead disable hover via the disabled state. Use `not-disabled:hover:*` (Tailwind v4 supports `not-disabled:`) OR split into plain `hover:*`/`active:*` plus a `disabled:` reset, e.g. primary: `hover:bg-accent-deep hover:-translate-y-px hover:shadow-[0_5px_14px_rgba(47,82,70,0.22)] active:translate-y-0 active:shadow-[0_2px_6px_rgba(47,82,70,0.2)] disabled:hover:bg-accent disabled:hover:translate-y-0 disabled:hover:shadow-none`. Apply the same to ghost. Verify in a browser that both the <a> and <button> render paths animate. The global a,button transition (global.css:75-79) already covers timing.
